# 前端完善路线图

> 状态：规划基线（2026-11-22）
>
> 本文恢复并整理此前讨论确定的前端方向与阶段计划。已实现项目以当前主分支代码为准；未验证的项目不标记为完成。本计划用于后续拆分 PR 和跟踪，不代表所有功能已承诺实现。

## 目标与设计原则

目标是把 GKD Subscription Hub 做成完整的平台管理端（Full Platform），采用专业、统一的管理界面（Professional UI），而不是只堆叠独立功能页。

- 先建立统一的类型、API 访问层和 AdminLayout，再扩展业务页面。
- 延续 Vue 3 + Vite + Naive UI；使用 Bun workspaces 与 bun.lock 管理工作区，使用 Biome 进行代码质量检查。
- 以 `zclzone/vue-naive-admin` 的成熟管理端结构作为可裁剪参考/基础，不为套模板而重写已有业务。
- 视觉方向采用 Fluent-inspired；单一 CSS Design Tokens 是唯一设计源，Naive UI 主题和业务 CSS 均映射到 Tokens，禁止另起一套硬编码视觉规范。
- 管理端默认中文；只有项目整体协作氛围明确以英语为主时才使用英语。
- 面向订阅客户端的响应优先保证原始订阅内容；浏览器访问再提供友好预览。

## 阶段 0：基础架构与统一壳层

目标：先解决页面之间的结构和数据访问不一致，避免每个页面各自实现。

- [x] 梳理现有路由、页面、组件、样式和 API 调用。
- [x] 统一项目与 Explorer 领域类型及主要 API 响应类型，移除 Explorer 页面内的宽泛 `Record<string, any>`。
- [x] 建立统一 API client 基础：统一鉴权头、响应解析、结构化 HTTP 错误与 401 会话失效处理。
- [x] 为项目与 Explorer API 调用声明响应类型；补充 API client 请求头和 401 会话失效单元测试。
- [x] 建立共享 AdminLayout：顶部栏、侧边导航、移动端导航、内容容器；订阅管理和 Explorer 共用。
- [x] 统一会话存取、退出行为与受保护路由；独立登录页验证凭据后再写入会话。
- [x] 将共享页面基础样式迁入全局样式，并继续使用 Design Tokens 作为视觉变量来源。
- [ ] 明确组件复用边界，不为抽象而抽象。

**验收标准**

- 所有受保护管理页面复用同一布局和导航。
- 页面不再自行拼接重复的鉴权/API 错误处理。
- 桌面端与移动端导航行为一致。
- 类型检查、Lint、格式检查和构建通过。

## 阶段 1：仪表盘与订阅源管理

目标：让管理员能快速判断系统状态，并高效管理订阅源。

- [x] 仪表盘概览：项目数、文件数、异常数、尚未检查数量、最近检查情况和异常项目。
- [x] 订阅源列表、分组展示、搜索和状态筛选（已有基础实现）。
- [x] 添加订阅源、指定分支/分组、单项目刷新和删除（已有基础实现）。
- [x] 分组折叠状态；分组级操作入口仍待完善。
- [x] 批量选择、批量刷新与批量删除；删除前确认影响范围，失败项保留选择，401 终止剩余操作并报告未执行项。
- [ ] 订阅源详情/配置表单及 Zod 校验。
- [ ] 空状态、错误状态、加载状态和危险操作确认的一致化。

**验收标准**

- 常用订阅管理操作无需离开列表页面。
- 分组、筛选和搜索组合工作正确。
- 批量操作明确展示影响范围和执行结果。
- 移动端仍可完成核心管理操作。

## 阶段 2：监控与文件管理

目标：提供系统运行状态、更新检查与订阅文件的可观测性。

- [ ] 监控概览：最近运行、失败情况、关键运行状态。
- [ ] 更新/检查任务状态与错误信息可追踪。
- [ ] 文件列表与文件元信息展示。
- [ ] 文件预览：JSON5 与 Markdown 友好展示。
- [ ] 高级 JSON5 编辑器（仅在明确编辑需求、校验和保存边界后实施）。
- [ ] 浏览器与 GKD 客户端内容协商验证：GKD 默认获得原始订阅，浏览器获得友好预览。
- [ ] 文件/版本内容与 commit SHA 绑定，确保版本可复现。

**验收标准**

- 能定位最近一次检查/更新失败的原因。
- 文件预览不会改变实际分发给 GKD 的原始内容。
- 版本引用固定到 commit SHA。
- 编辑（若启用）必须有校验、保存反馈和失败保护。

## 阶段 3：历史记录与高级管理

目标：补齐可追溯性和管理能力，但不扩大不必要的权限系统复杂度。

- [ ] 历史记录：订阅源变更、文件版本、检查/更新事件。
- [ ] 版本差异与历史版本定位。
- [ ] 高级管理操作与必要的风险提示。
- [ ] 批量操作结果与审计信息。
- [ ] 根据真实使用反馈决定是否增加更多管理能力。

**明确暂不纳入**

- 多用户、角色权限/RBAC。
- 在线协作编辑。
- 未经需求确认的复杂工作流或大型状态管理系统。

## 阶段 4：体验、稳定性与发布验收

目标：让已实现功能在真实设备和异常场景下可靠工作。

- [ ] 统一响应式断点和窄屏布局。
- [ ] 验证键盘可操作性、焦点状态、表单可访问性。
- [ ] 统一加载、空数据、错误、成功、确认等反馈。
- [ ] 关键业务逻辑和页面交互测试。
- [ ] 验证未登录、会话失效、网络失败、API 失败、空数据等边界。
- [ ] 验证桌面与移动端真实浏览器体验。
- [ ] CI、构建、部署和线上 Smoke Test。
- [ ] 更新 README、功能文档和 AGENTS.md。

**验收标准**

- 核心页面在窄屏和桌面端均可用。
- 关键路径有自动化测试或明确的手动验收记录。
- CI 与生产 Smoke Test 通过。
- 文档与实际功能保持一致。

## 执行约定

1. 每个阶段拆成可独立评审的 PR，不把所有 UI 改造塞进一个大 PR。
2. 先做基础架构和壳层，再推进页面；避免并行制造重复布局。
3. 每个 PR 同步更新相关文档和必要测试。
4. 不以“CI 通过”代替功能验收；涉及浏览器交互的功能必须验证实际页面行为。
5. 不执行真实生产扫描或写入生产数据作为普通 UI Smoke Test。
