# 需求工程规范

本规范适用于跨页面、跨模块、持久化数据、权限/安全边界、部署流程或明显影响用户工作流的需求。小型修复可以直接写在 Issue/PR 中，不要求为每个改动创建独立需求文档。

## 1. 需求质量标准

一条可执行需求应当：

- **明确**：只表达一个主要行为，避免“更好、更快、更友好”等不可验证词语。
- **必要**：说明用户问题和预期价值，不把实现方案伪装成需求。
- **可行**：符合 Cloudflare Workers、KV、GitHub API 配额和现有预算/维护能力。
- **可验证**：能通过测试、日志、浏览器行为或明确的人工验收判定。
- **可追踪**：从需求 ID 能定位验收标准、测试、PR 和文档。
- **有边界**：明确非目标、权限边界、异常行为和不处理的情况。

## 2. 需求分层

### 产品目标

说明为什么做、谁受益、成功如何衡量。避免直接从“加一个按钮”开始。

### 功能需求（FR）

描述系统对外可观察的行为，例如登录、注册项目、批量刷新、扫描暂停和错误反馈。使用稳定编号：FR-001、FR-002。

### 非功能需求（NFR）

至少评估与本项目相关的维度：

- 安全：鉴权、Secret、权限、输入校验、数据暴露。
- 可靠性：超时、重试、幂等、部分失败、恢复能力。
- 性能：请求数量、并发、延迟、资源消耗。
- 可用性：空/加载/错误状态、键盘、移动端和可访问性。
- 可维护性：模块边界、类型、测试、文档。
- 成本与配额：Workers/KV 使用、GitHub API 主/次级速率限制。
- 兼容性：历史 KV 记录、已有 API 客户端、旧订阅链接。

不要机械罗列全部维度；不适用时写明原因。

### 验收标准（AC）

使用稳定编号 AC-001。优先使用 Given / When / Then：

~~~text
Given：用户已登录且存在两个可管理项目
When：用户批量刷新当前筛选结果
Then：项目按规定顺序执行；逐项反馈成功/失败；401 时停止剩余请求
~~~

验收标准描述结果，不限定无关的内部实现。

## 3. 需求文档模板

~~~markdown

- 状态：Draft / Ready / In Progress / Accepted / Rejected
- 需求负责人：
- 目标版本/阶段：
- 关联 Issue / PR：

## 背景与问题
当前用户遇到什么问题？证据是什么？

## 目标与成功指标
预期改变什么？如何判定有价值？

## 用户与场景
主要用户、触发条件、前置状态。

## 功能需求
- FR-001：
- FR-002：

## 非功能需求
- NFR-001：
- NFR-002：

## 非目标
明确本次不处理什么。

## 验收标准
- AC-001：
- AC-002：

## 异常与边界
鉴权失效、网络失败、限流、空数据、重复请求、部分成功等。

## 数据/API/迁移影响
KV schema、请求响应、历史记录兼容、回滚方式。

## 安全、成本与运行约束
Secret、Preview/Production、GitHub 配额、Workers/KV 成本。

## 测试映射
需求 ID -> 测试文件/用例 -> PR/Commit。

## 未确认问题与假设
把推测标为待证实，不把它写成已确认事实。
~~~

## 4. 从需求到交付的追踪链

每个重要需求应形成：

**用户问题 → FR/NFR → AC → 测试用例 → 实现 PR → 文档/验收记录**

- 一个 AC 可以对应多个测试；一个测试也可覆盖多个 AC，但要能解释映射关系。
- 需求改变时同步修改 AC 和测试，不只改描述。
- PR 描述引用 FR/AC ID，说明哪些完成、哪些延期。
- 测试通过只能证明对应测试覆盖的行为，不自动证明所有需求满足。
- 手动浏览器验收应记录设备/视口、步骤和结果。

## 5. 范围与优先级

- P0：安全、数据丢失、生产可用性、阻断主要流程。
- P1：核心用户工作流缺陷、明显质量门禁缺口。
- P2：体验改进、维护成本降低。
- P3：非必要优化或探索性想法。

拆分需求时优先形成可独立验收的垂直切片，不按前端/后端机械分割。每个切片有明确输入、输出和失败行为。

## 6. Ready / Done

### Definition of Ready

- 用户问题和目标清楚。
- FR/NFR/AC 可验证。
- 非目标和依赖明确。
- 风险、安全、数据迁移和成本已评估。
- 不确定项已标记，不把关键未知数藏在实现阶段。

### Definition of Done

- 验收标准有对应测试或人工验收证据。
- 格式、Lint、类型、测试和构建结果真实记录。
- API、README、工程文档、Agent 指令按需同步。
- 未完成项、风险、回滚和部署边界明确。
- 未执行的测试不写成通过；未授权的合并/部署不视为默认步骤。

## 7. 用 AI Agent 辅助需求分析

Prompt 至少提供：

1. 用户问题与目标，不只给实现想法。
2. 当前源码/日志/截图/配置等证据。
3. 已知约束与不可触碰范围。
4. 要求 Agent 先区分事实、假设、未知项。
5. 产出 FR/NFR/AC、边界情况和风险。
6. 让用户确认重要取舍后再实施。
7. 最终交付逐条映射 AC、测试和文档。

Agent 不得把猜测补成事实，也不得为满足验收而删除原有测试断言或弱化安全约束。
